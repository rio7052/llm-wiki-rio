`/meeting-ingest` — 회의 **전사 스크립트나 손메모를 던지면** ① **원문을 그대로 보관**하고 ② **맥락으로 정리한 회의록**을 만들어 ③ 둘 다 위키에 남긴다. 남에게 건넬 판이 필요하면 PDF 도 뽑는다.

> **원문과 정리본은 다른 파일이다.** 원문은 나중에 "그때 정확히 뭐라고 했더라"를 확인하는 근거이고, 정리본은 읽고 실행하는 물건이다. 섞으면 둘 다 못 쓴다.
> 위키 schema 는 `CLAUDE.md`(§7.12 절차, §4.3 raw, §9 마스킹, §11.1 공유 산출물, §15 태스크 보드).
> 입력: `$ARGUMENTS`(파일 경로) 또는 대화에 붙여넣은 텍스트.

## 진행 순서

### 1. 입력 확보

- `$ARGUMENTS` 가 파일 경로면 그것을 쓴다. 비어 있으면 다운로드 폴더의 최신 후보를 보여주고 고르게 한다: `ls -t ~/Downloads/*.md ~/Downloads/*.txt 2>/dev/null | head -5`
- **구조부터 본다** — 통째로 읽지 않는다. 회의 스크립트는 보통 100KB 를 넘고 빈 줄이 절반이다.

```bash
F="<파일경로>"
grep -c "^### " "$F"                       # 타임스탬프 개수 = 회의 길이 감
grep -oE "^\*\*[^:：]{1,20}[:：]" "$F" | sort | uniq -c | sort -rn   # 발화자 분포
grep -c . "$F"                             # 빈 줄 뺀 실제 줄 수
```

- 본문은 **빈 줄을 걷어내 청크로** 읽는다. 한 번에 600~700줄이 적당하다.

```bash
sed -n '<시작>,<끝>p' "$F" | grep . | sed 's/^\*\*//; s/：/: /'
```

### 2. 회의 메타 확인 — 반드시 사용자에게 묻는다

**전사본에는 표시명만 있고 실제 참석자가 없다.** 추측하지 말고 묻는다.

- **일시·소요 시간** (스크립트 타임스탬프로 추정한 값을 제시하고 확인받는다)
- **참석자** — 소속별로. 예: `우리 — <나>, <담당자> / <상대 기관> — <직함 있는 분들>`
- **공유한 자료**가 있으면 무엇인지

⚠️ **화자 분리는 대개 부정확하다.** 현장에서 한 마이크를 여럿이 쓰면 여러 사람의 말이 한 표시명으로 묶인다. **표시명 하나 = 사람 하나로 단정하지 않는다.** 정리본에서 발언자를 특정할 때는 내용으로 판별되는 경우만 쓰고, 애매하면 소속으로 적는다.

### 3. 원문 보관 — `raw/notes/YYYY-MM-DD-<slug>-transcript.md`

원문을 **거의 그대로** 옮기되 세 가지만 손댄다.

1. **frontmatter + 머리말**을 붙인다 (`type: report`, `report_kind: daily`, `period`, `tags: [meeting, transcript, raw, ...]`).
2. **마스킹**(§9) — 개인·고객 식별 정보, 계정·토큰, 급여·계약액. **raw 도 커밋되므로**(§4.3) 여기서 반드시 거른다.
3. **발화자 표시명을 실제 소속·이름으로** 바꾼다. 섞여 있으면 소속으로.

머리말에 **전사 품질과 화자 분리의 한계를 명시**한다 — 나중에 이 파일을 읽는 사람이 오해하지 않게.

```markdown
✅ 원문 파일 머리말에 둘 것
음성 인식 전사본 원문이다. 자동 전사라 오탈자가 많고 화자 분리가 정확하지 않다 —
한 마이크를 함께 쓰셨기 때문에 `<소속>` 으로 표시된 발언에는 여러 분의 말씀이 섞여 있다.
```

### 4. 정리본 작성 — `raw/notes/YYYY-MM-DD-<slug>-minutes.md`

**머리에 둘 것은 회의 사실뿐이다.**

```markdown
✅ 정상
> **일시** YYYY-MM-DD 10:00~11:53
> **참석** 우리 — <나>, <담당자> / <상대 기관> — <직함 있는 분들>
> **자료** <화면 공유한 문서 이름과 판>

❌ 위반 — 작업 메타를 정리본에 섞는다
> 음성 전사본을 정리한 것이라 오탈자가 많고 화자 분리도 완전하지 않다.
> 맥락으로 복원했으며 확신이 서지 않는 대목은 옮기지 않았다.
```

전사 품질·복원 방식·마스킹 여부는 **원문 파일 머리말 몫**이다. 정리본은 회의 내용만 담는다.

**본문 구성**

| 절 | 넣을 것 |
|---|---|
| **큰 줄기** (선택) | 여러 안건이 하나의 주장으로 모이면 맨 앞에 그 한 문장. 안 모이면 넣지 않는다 |
| **주제별 절** | 안건 단위. 배경 → 상대가 제기한 것 → 우리 답변 → 합의·액션 순 |
| **우리가 할 일** | `# / 항목 / 담당` 표. 회의에서 나온 액션을 빠짐없이 |
| **다음 일정** | 날짜·형식(방문/컨콜)·준비물 |
| **관련 페이지** | 이전 회의록, 원문 파일, 공유 자료 경로 |

**정리 원칙**

- **오탈자는 맥락으로 복원하되, 확신이 서지 않으면 옮기지 않는다.** 추측으로 채우면 나중에 그것이 사실로 굳는다.
- 상대가 **같은 말을 여러 번 강조했으면** 그것이 그 회의의 핵심이다. 분량이 아니라 반복 횟수로 무게를 잡는다.
- **인용이 살아 있는 대목은 인용으로 남긴다.** 요약하면 힘이 빠지는 문장이 있다.
- 수치·고유명사는 원문대로. 다만 **식별 정보는 마스킹**(§9).

### 5. (선택) PDF — `wiki/assets/reports/`

남에게 건네거나 보관용 판이 필요할 때만 뽑는다. md 만으로 충분하면 건너뛴다.

```bash
bash tools/md-to-pdf.sh <입력.md> wiki/assets/reports/<출력.pdf> "<문서 제목>"
```

- 파일명은 `YYYY-MM-<slug>-minutes.pdf` · `YYYY-MM-<slug>-transcript.pdf` (§11.2 kebab-case). **md 도 pdf 와 같은 접미사 규칙을 쓴다** — 정리본은 `-minutes`, 원문은 `-transcript` 로 항상 짝을 이룬다. 접미사 없는 맨이름을 쓰면 폴더에서 어느 쪽인지 알 수 없다.
- 스크립트는 pandoc → Chrome headless 로 뽑는다. 경로는 `PANDOC`·`CHROME` 환경변수로 덮어쓸 수 있다. 둘 중 하나가 없으면 **PDF 단계만 건너뛰고** md 는 그대로 둔다.

### 6. 반영

- **index.md** — 새 페이지가 wiki 쪽이면 추가. `raw/notes/` 만 만들었으면 생략.
- **log.md** — `## [YYYY-MM-DD] meeting | <회의명>` 으로 원문·정리본(·PDF) 경로와 **핵심 결정 3~5줄**을 남긴다(§8.2).
- **오늘 일일 리포트** — `## 한 일` 에 한 줄, 해당 체크리스트가 있으면 완료 처리.
- **태스크 보드 반영은 제안한다**(§15) — 액션이 여러 건이면 어느 것을 보드에 올릴지 묻는다. 임의로 다 올리지 않는다.
- **공유 할 일에 해당하는 액션은 GitHub issue 초안을 만들어 승인받는다**(§15.1·§17.3). 담당이 다른 사람이거나, 남과 약속한 마감이 있거나, 결과를 다른 파트나 외부가 받는 액션이 해당한다. `tools/company-wiki.py task-new` 를 `--yes` 없이 실행해 미리보기를 보여 주고, 승인받은 뒤에만 `--yes` 로 만든다. `--assignee` 로 회의에서 정한 담당자를 지정할 수 있다. 개인 할 일에 해당하는 액션은 개인 보드에만 둔다.
- **전사 공유가 필요한 회의라면** 정리본을 전사 위키 `raw/meetings/YYYY-MM-DD-<slug>.md` 로 올릴지 묻는다. 전사 기준(§9: 농가·업체명 실명, 개체번호·급여·계약액 가림)으로 다시 거른 판을 만들고 `python tools/company-wiki.py mine-put --file <정리본.md>:raw/meetings/<파일명> --slug <slug> --op meeting --title "<회의명>"` 을 `--yes` 없이 돌려 미리보기를 보여 준 뒤, 승인받으면 `--yes` 로 올린다. 원문 전사본은 올리지 않는다.
- 회의에서 굳은 **결정·개념**이 있으면 `decisions/`·`concepts/` 승격을 한 줄 제안한다(§7.6). 회의록을 남겼다고 지식이 남는 게 아니다.

### 7. 마무리

- 한 줄 상태: `원문 N줄 / 정리본 M절 / 액션 K건`.
- **상대에게 건넬 판이라면** 「우리가 할 일」 표가 내부용임을 짚고, 뺀 판이 필요한지 묻는다.

## 안전·톤

- **원문은 raw 이므로 만든 뒤 수정하지 않는다**(§4.3). 정리본은 작성 당일까지 mutable.
- 대외로 나가는 문서는 마스킹을 더 엄격히(§11.1) — 가격·계약액·급여·인사 사정·고객 식별 정보를 뺀다.
- 사용자와의 대화는 **존댓말**, 문서 본문은 **평어체**(§3). 다만 **회의 참석자에 대한 호칭은 높인다**.
- 회의에서 나온 본인 생각·판단이 드러나면 brain note 를 한 줄 제안한다(§16).
